# 61 判决性实验结果（C++ 节点）

回应三方评审提出的判决性实验，全部在 RDK X5 真机执行。
原始输出：`/tmp/probe/soak.txt`（板端）。

## 1. phase 1 — 1920x1080@30 拼接 soak，约 12 分钟

这是对 A1 的 D-1 攻击（"单线程定时器模型在 1080p 下不成立"）的判决实验。

| 指标 | 实测 | 判据 | 结论 |
|---|---|---|---|
| 图像帧数 | 21450 帧 / 约 715 s = **30.0 fps** | ≥ 29.0 Hz | **通过** |
| IMU 包数 | 144484 包 / 约 715 s = **202 Hz** | ≈ odr(200) | **通过** |
| 进程 RSS | 63704 kB → 63520 kB（12 个采样点单调微降） | 无持续增长 | **无泄漏** |

**裁决：D-1 攻击被实测推翻。** 单线程 executor + 两个 wall timer 在
1920x1080 拼接（每帧 6.2 MB、约 373 MB/s）下仍能满帧运行，且 IMU 不受影响。
会话期间未出现丢帧迹象（帧数增量恒定 150/5 s）。

补充说明：本次以 `stderr` 日志计数为准，未回读 `gs130_available_camera()`，
因此"队列是否积压"未直接测量；但帧数增量长期恒定表明没有持续积压。

## 2. phase 2 — 第二个持有者抢流：E8 看门狗

对 C1 的 TC-23/TC-24（"该缺陷没有任何症状，必须钉住"）的判决实验。

第一个节点（1920x1080）持续运行期间启动第二个节点（640x480）：

```
第一个节点：frames 冻结在 21507，随后 imu 也停止，接着 imu read failed with 4 (HW_ERROR)
第二个节点：frames=1200（拿到帧流），imu=0（拿不到 IMU）
看门狗：     "no camera frames for about 10 s ..."  ERROR 恰好打印 1 次
```

**结论**：
1. 与 Python 版一致，第二个打开者不报错、直接抢走帧流。
2. 但 C++ 复测补充了一条 Python 版没观察到的事实：**IMU 也会停止并转为 `HW_ERROR(4)`**，
   即抢流之后先到者并非"只有图像停"。
3. 看门狗准确触发一次，未刷屏。

## 3. 由此暴露并修复的两个实现缺陷

| 缺陷 | 实测证据 | 修复 |
|---|---|---|
| 看门狗文案错误：声称 "while the IMU still streams" | 实测 IMU 同时也停止并返回 HW_ERROR(4) | 改为不假定 IMU 仍在流，并说明抢流也会让 IMU 读取失败 |
| 读取故障刷屏：`poll_imu` 每次失败都打一行 ERROR，一个 tick 最多 64 行 | 日志中出现连续多行 `imu read failed with 4` | 改为"每个故障状态只报一次"，恢复后自动复位 |

## 4. 测量方法本身的坑（写入测试方案）

| 现象 | 说明 |
|---|---|
| `ros2 topic hz /imu/data` 报 150 Hz，而节点内部计数为 202 Hz | CLI 订阅端（Python、默认 depth 10）跟不上 200–500 Hz 的小消息。**IMU 速率必须用节点自身计数或 C++ 订阅端测量**，不能用 `ros2 topic hz` |
| 用 `ros2 topic echo --once` 采样图像时间戳，偏差在 ±300 ms 抖动 | 该命令的发现与接收延迟远大于真实漂移，无法用于漂移判定。改用 IMU 接收延迟趋势法（见 `62_drift_result.md`） |
| 前一次 odr 实验被残留进程污染 | 一次 `odr=100` 被判为"可用"，实为残留 owner 抢流的假象。**每次实验前必须确认无 `camera_node` 残留**，否则结论无效 |
