# 40 工程流程记录 — gs130_ros v0.1.0

本文件记录本项目按软件工程流程推进的实际过程：哪些会议开过、谁参加、
产出什么文档、哪些结论被实测推翻、最终冻结了什么。
所有阶段产物都在 `ros/docs/`，实现产物在 `ros/gs130_ros/`。

---

## 1. 组织

四个团队，每团 3 名独立评审/开发 Agent（互不可见，只能通过文档与总架构师交互）：

| 团队 | 成员 | 职责 |
|---|---|---|
| 产品经理团 | PM-1 需求评审、PM-2 接口需求、PM-3 场景与兼容性 | 用户故事、API 契约、场景分析 |
| 技术研发团 | DEV-1 架构设计、DEV-2 接口冻结、DEV-3 实施计划 | 方案、契约、迭代拆分 |
| 测试团 | QA-1 测试计划、QA-2 验收判据、QA-3 风险与安全 | 验证方案与门禁 |
| 用户测评团 | UX-1 首轮用户反馈、UX-2 可用性评审、UX-3 生态集成预期 | 用户视角挑战设计 |

总架构师（本 Agent）负责：平台实测、冲突裁决、实现、真机验证、发布。

**团队纪律（写入每个 Agent 的任务书）**：只读写自己那一个文档；不得 ssh 板卡、
不得运行相机、不得修改 `python/`、不得 commit/push。
板卡是共享的真实硬件，历史上曾因误操作需要重启，因此硬件访问被收归总架构师独占。

## 3. 关键节点：第 ⑥ 步为什么重要

各团在**没有板卡**的条件下只能读源码与推断，产出的契约里混入了若干
"看起来合理"但在真机上会失败的规定。总架构师在实现前先做了一轮
不占用相机的验证实验（用合成 NV12 图打通既有 codec + websocket 链路），
一次性证伪了三条，并发现一条会直接导致段错误的约定：

| 编号 | 实测结论 | 影响 |
|---|---|---|
| E1 | 图像 QoS 必须 RELIABLE | 三个文档建议的 BEST_EFFORT 会让网页**静默黑屏**，双方都不报错 |
| E2 | `Image.height` 必须是真实高 | 按冻结书的 `H*3//2` 会让 `hobot_codec` **段错误（-11）** |
| E3 | `msg.data` 必须整块赋值 | 直接赋 `bytes` 触发 rclpy 逐元素校验，1.38 MB 一帧 **1103.87 ms**（正确写法 1.36 ms） |
| E4 | 链路 30 fps 可用、nginx 是孤儿 | 既有无需改造即可用；但 nginx 不随 launch 退出 |
| E5 | SDK 时间戳是 CLOCK_MONOTONIC | 直接进 `header.stamp` 会破坏 tf/message_filters/rosbag |
| E6 | SDK 硬件拼接可用 | 无需任何手工拼接代码，且 RAW 模式不能拼接 |

这些结论被回灌给仍在写作的三个 Agent，其余已完成文档在评审阶段按事实修正
（`10_architecture.md`、`21_acceptance_criteria.md`、`32_integration_expectations.md`
均已按 E1–E7 重写相应章节；`11_interface_freeze.md` 顶部加入修订通知）。

**流程教训**：接口契约在板端实测之前冻结，是本次流程里最大的风险来源。
正确顺序应是"最小实验 → 冻结契约 → 大规模实现"。

## 4. 需求与范围裁决

- 采纳：单命令拉起相机 + 网页看图；双目/IMU/标定以标准消息发布；复用既有节点；
  相机独占冲突要可诊断；关停必须释放相机。
- 拒绝（过度开发）：自研网页/编码器/深度网络、自定义消息、运行期动态重配置、
  多相机实例、ROS 1、零拷贝改造、把标定解算成点云。
- 延后（非 v0.1.0）：`hobot_stereonet` 联调（需 `top_bottom` 布局且其 launch 会拉
  `mipi_cam`，与相机独占冲突）、IMU 噪声协方差建模、长时漂移补偿。

## 5. 被实测推翻的评审意见（保留记录以避免重复讨论）

| 评审意见 | 出处 | 实测结论 |
|---|---|---|
| 图像用 `SensorDataQoS`（BEST_EFFORT） | 多份文档 | 错，必须 RELIABLE（E1） |
| NV12 `height = H*3//2` | 冻结书 §3.1 | 错，会段错误，必须为真实高（E2） |
| 驱动侧手工 `concatenate` 左右目 | 冻结书 §3.3 | 不需要，SDK 硬件拼接（E6） |
| IMU 被相机帧率门控（200/30 一批） | UX-1 | 错，实测 202.9 Hz 独立于 30 fps |
| 零拷贝是待验证的优化方向 | UX-3 初版 | 无意义，SDK 帧本身就是 `malloc` 缓冲，正确路线是一次拷贝（E3） |
| v0.1.0 不发布 TF | 冻结书 §0.2 | 改为默认发布：外参是真实硬件能力，成本为零（UX-3 复评支持） |

## 6. 迭代与真机缺陷

| 迭代 | 目标 | 结果 |
|---|---|---|
| 迭代 1 | 最小可见：节点 + `image_message` 契约 + launch | 真机跑通，暴露缺陷 #1（stamp 类型） |
| 迭代 2 | IMU + 标定 + TF | 30 fps / 203 Hz 稳定输出 |
| 迭代 3 | 关停与资源释放 | 暴露缺陷 #2（SIGINT 中断释放），修复后干净退出 |
| 迭代 4 | Web 端到端 + 抓帧目视 | 网页 HTTP 200，抓帧解码为正确双目图 |

缺陷 #2 是安全相关：若关停被中断，相机可能被残留进程持有，后续任何程序都无法初始化。

## 7. 发布判定

真机证据见 `25_test_report.md`：L1 单元 9/9、L2 构建、L3 集成、L4 端到端、L5 关停全部通过。
未覆盖项（`mode:=rect`、`mode:=raw` 组合、其它分辨率、`stereo_layout:=none`、
长时漂移、stereonet 联调）已在报告中**明确标注为未验证**，不得当作已验证。

代码评审与契约评审的结论见 `23_code_review.md`、`24_contract_review.md`、
`33_user_review_round2.md`。
